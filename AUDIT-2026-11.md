# EduManager Cloud — Production Audit (2026-11)

**Repository:** `Dahtmusa/EduManager`  
**Reviewed ref:** `main`  
**Reviewed source snapshot:** `index.html` (1,056,571 bytes; 9,045 lines), `sw.js`, `supabase/migrations/0001_init.sql`, `PHASE-0-DEPLOY.md`, and the attendance service path discovered in the repository tree.  
**Audit type:** Static source/configuration review. No production database, Supabase dashboard, Netlify deployment, secrets, or live tenant records were accessed.

## Executive summary

The current repository contains several material differences from the intended Phase 1 architecture. Most importantly, legacy browser persistence and client-side school credentials remain in the source, while the Supabase RLS model appears to expect authenticated school users. The boot sequence also appears to request protected master data before rendering the owner sign-in UI. These issues should be resolved before onboarding, billing, or broad tenant expansion.

**Do not merge schema expansion (PR-B) or enable self-service onboarding until the P0/P1 issues below have been remediated and tested.** Preserve BNFODIO and all existing results, payments, attendance, and Hifz/Tahfiz data.

## Severity-ranked findings

### P0 — Blocker: owner authentication bootstrap appears unreachable for anonymous visitors

**Evidence:** `boot()` (around line 5596) initializes Supabase and calls `cloudPull('__master__')` before `renderAuth()` displays the owner sign-in UI. The reviewed `0001_init.sql` policy for `school_data` grants authenticated access to owner/member rows; anonymous users have no read access. The owner password sign-in is invoked later by the owner login handler (around line 3080).

**Impact:** On a fresh anonymous session, the protected master-row read can fail before the owner login screen is made available. This is an authentication bootstrap/RLS ordering conflict.

**Required fix:** Render the unauthenticated shell first; do not request protected data until a valid Supabase session exists. Add explicit loading/error states and verify fresh-session owner sign-in against production-equivalent RLS.

### P0 — Blocker: school login remains a legacy client-side credential check

**Evidence:** `schoolLogin()` (around line 3097) compares a submitted password against a value in `DB.users` (`x.password===p`). The reviewed flow does not establish a Supabase Auth session for the school user.

**Impact:** RLS-protected cloud reads/writes cannot reliably operate for school users without an authenticated Supabase session. Storing/checking passwords in a downloadable client-side data structure is not a secure authentication boundary.

**Required fix:** Move school login to Supabase Auth. Store only non-secret user/profile metadata in application data. Migrate credentials safely; never log or expose plaintext passwords.

### P1 — Critical: browser localStorage persistence remains in the current source

**Evidence:** `loadStore`, `saveStoreLocal`, `loadBase`, `saveBase`, and `backupSnapshot` still use localStorage (around lines 846–880); `boot()` invokes local loading; `pullRow()` can return `STORE[id]` after a failed request; write paths call local persistence and backup helpers.

**Impact:** This contradicts the stated cloud-only Phase 1 requirement. A network failure can fall back to stale local data, and browser backups may retain school records on shared devices.

**Required fix:** Remove legacy data mirroring and stale fallback only after confirming the cloud read/write paths and recovery UX. On cloud failure, fail visibly; never silently treat stale browser data as authoritative. Add regression tests proving no school data is written to localStorage.

### P1 — Critical: school passwords appear in application data and owner UI

**Evidence:** School login compares `DB.users` password values in the browser; the owner registry area (around line 3233) displays administrator username/password information.

**Impact:** Anyone able to read the application data or owner screen may obtain reusable credentials. This is a direct account-compromise risk.

**Required fix:** Remove plaintext password fields and displays. Use Supabase Auth password handling and safe account recovery/reset flows. Review historical data and logs for exposed credentials; rotate affected passwords.

### P1 — Critical: broad school-data row access is not sufficiently role-scoped

**Evidence:** The reviewed RLS policy permits a school member to select the school's `school_data` row, which contains a broad JSON document (pupils, staff, results, finance, attendance, Hifz and related records). The `__master__` row policy also appears to permit authenticated users to select that row, not just the owner.

**Impact:** A low-privilege member may be able to read substantially more information than their role requires. The master row may expose owner/admin metadata.

**Required fix:** Define explicit role and record-level authorization before adding more school roles or tenants. Restrict `__master__` to the exact owner role. Prefer normalized tables and narrowly scoped RPC/API operations for sensitive domains. Test RLS with anon, owner, school admin, teacher, and parent identities.

### P1 — Critical: owner role check is permissive when role metadata is absent

**Evidence:** Owner login check around line 3080 uses a conditional equivalent to `if(role && role!=='owner')`, which rejects a wrong non-empty role but does not reject a missing role.

**Impact:** Missing role metadata may not be rejected at this client-side gate. Client checks are not a substitute for RLS, but the UI guard should fail closed.

**Required fix:** Require `app_metadata.role === 'owner'` exactly, and enforce the same rule in database policies.

### P1 — High: restore path may report success without verifying the database write

**Evidence:** `doRestore()` (around line 1011) performs a direct upsert outside the normal CAS helper and the reviewed path does not reliably gate success on the returned Supabase error.

**Impact:** A failed restore can be presented as successful, leaving the user believing data was restored when it was not. Direct upsert can also bypass concurrency protections.

**Required fix:** Route restore through a validated, awaited commit path; check all returned errors; verify the committed revision before showing success. Preserve a recoverable pre-restore snapshot and require explicit confirmation.

### P1 — High: compare-and-swap does not protect first insert from concurrent writers

**Evidence:** `_commitRowCAS()` protects updates using `updated_at`, but when a row is absent it uses an upsert path without an atomic insert-if-absent condition.

**Impact:** Two concurrent first writers can race and overwrite one another during initial school-row creation.

**Required fix:** Use an atomic database-side insert-if-absent / uniqueness strategy or a transaction/RPC that handles create and update with a single concurrency contract. Add concurrent first-write tests.

### P2 — High: single JSONB document per school creates scaling and contention risks

**Evidence:** Most school state is stored in one `school_data.data` document. Owner boot uses `pullAllStrict()` to select `id,data` for all rows.

**Impact:** Every small update can rewrite a large document; concurrent users contend on one row; owner startup cost grows with all tenant data; role-scoped access is difficult.

**Recommendation:** Plan an incremental normalization roadmap by domain. Do not perform a big-bang migration. Start with high-sensitivity/high-write domains and retain compatibility adapters with reconciliation and rollback.

### P2 — Medium: restore/import paths need a complete consistency review

**Evidence:** Direct restore upsert bypasses the standard CAS helper. Import/restore paths require review for the same success/error and revision guarantees.

**Recommendation:** Inventory every write path (normal save, import, restore, admin edits, background jobs). Each must have consistent validation, authorization, durable acknowledgement, audit logging, and concurrency semantics.

### P2 — Medium: external scripts are not pinned with integrity metadata

**Evidence:** External CDN scripts are loaded from the document head; Supabase JS uses a floating `@2` version and Chart.js appears more than once in the reviewed page.

**Impact:** Supply-chain changes can alter runtime behavior; duplicate scripts increase payload and potential conflicts.

**Recommendation:** Pin exact tested versions, add SRI/crossorigin where supported, remove duplicates, and document an update process.

### P2 — Medium: extensive `innerHTML` usage needs sink-by-sink review

**Evidence:** Static scan found approximately 228 `innerHTML` occurrences. An `esc()` helper exists around line 1167, but this scan did not establish that every dynamic HTML, URL, attribute, style, or event-handler sink is safe.

**Impact:** Unescaped user-controlled content can lead to stored or reflected XSS.

**Recommendation:** Trace each dynamic value to its source; prefer `textContent` and DOM construction. Sanitize permitted rich text with a maintained allowlist sanitizer. Validate URL protocols and attribute contexts. Add adversarial tests. This audit does not claim a confirmed exploit.

### P2 — Medium: service-worker update routine has broad cache side effects

**Evidence:** `sw.js` is intentionally transparent/no-cache, but `forceUpdate()` unregisters service workers and clears all Cache Storage for the origin.

**Impact:** Clearing every origin cache can affect unrelated applications hosted on the same origin.

**Recommendation:** Scope cleanup to this application's own cache namespace and service-worker registrations; do not clear origin-wide caches.

### P2 — Medium: accessibility and dark-mode coverage are not demonstrated

**Evidence:** The page has responsive breakpoints, but the reviewed source does not demonstrate complete dark-mode support, consistent visible focus, screen-reader status announcements, or systematic keyboard navigation across all workflows.

**Recommendation:** Validate WCAG 2.2 AA (or the agreed AA baseline) using automated and manual testing. Include keyboard-only workflows, focus management, contrast, labels, error announcements, touch targets, reduced motion, and dark-mode contrast.

### P3 — Medium: audit logging exists as schema but operational coverage is unclear

**Evidence:** `audit_log` is created in the initial migration, but the reviewed source does not demonstrate a complete, tamper-resistant event-writing strategy for sensitive operations.

**Recommendation:** Define server-side audit events for auth/role changes, restore, exports, billing, sensitive record access, and administrative actions. Avoid logging secrets or unnecessary student data.

### P3 — Medium: automated regression coverage is not evidenced

**Recommendation:** Establish repeatable tests for authentication/RLS, CAS, restore, merge3, marks/results calculations, attendance, fees/payments, Hifz/Tahfiz scoring, 604-page Mushaf mapping, and coverage application before major UI or schema changes.

## Fix now vs later

### Must fix before PR-B / onboarding
1. Resolve owner authentication bootstrap ordering.
2. Replace client-side school password checks with Supabase Auth.
3. Remove plaintext passwords from data and UI; rotate exposed credentials.
4. Eliminate localStorage school-data fallback and stale-data success paths.
5. Restrict `__master__` to the exact owner role.
6. Define and test role-scoped access to sensitive school records.
7. Make restore success depend on a verified durable commit.
8. Make first-row creation concurrency-safe.
9. Establish a regression baseline for BNFODIO-critical workflows.

### Can be staged after the blockers
- JSONB normalization by domain.
- UI modernization and full dark-mode/accessibility pass.
- CDN pinning/SRI and duplicate script cleanup.
- Complete XSS sink remediation.
- Service-worker cache scoping.
- Comprehensive audit-log coverage and operational monitoring.

## BNFODIO data-safety requirements

- Do not truncate, delete, reseed, or overwrite live tenant data.
- Do not run schema/data migrations against production as part of this audit.
- All future schema changes must be additive/backwards-compatible first, with explicit preflight checks and rollback instructions.
- Preserve issued report cards and existing print output.
- Preserve Hifz/Tahfiz scoring semantics, page mapping, evaluations, and coverage behavior.
